# План разработки клиента Google Drive для Linux на Go и Qt

**Дата:** 17 октября 2026 года  
**Обновлено:** 30 октября 2026 года  
**Формат:** AppImage для x86_64  
**Назначение:** монтирование «Моего диска» Google Drive как каталога Linux

## 1. Согласованные требования

| Область | Решение |
|---|---|
| Язык | Go |
| Графический интерфейс | Qt 6 Widgets |
| Доступ к файлам | Чтение и запись уже в первом пригодном к использованию выпуске |
| Область Drive | Только «Мой диск»; общие диски и «Доступные мне» пока вне объёма |
| Точка монтирования | Пользователь выбирает папку в интерфейсе; диск монтируется при запуске приложения |
| Интерфейс | Графическое окно и значок состояния для GNOME и KDE Plasma |
| Аккаунты | Один аккаунт Google |
| Без сети | Чтение доступного в кэше; изменения сохраняются локально и отправляются позже |
| Успешное офлайн-сохранение | Данные надёжно записаны в локальную очередь, но ещё могут отсутствовать в Drive; статус должен быть виден пользователю |
| Конфликт версий | Сохранить обе версии рядом в каталоге и показать уведомление |
| Удаление | Переносить файл в корзину Google Drive; без сети ставить действие в очередь |
| Google Docs, Sheets, Slides | Показывать файлами-ссылками, открывающими документ в браузере |
| Кэш | Настраиваемый; по умолчанию 1 ГБ для вытесняемых данных |
| Офлайн-доступ | Пользователь может закрепить отдельные файлы и папки как «Доступно офлайн» |
| Превышение лимита кэша | Закреплённые файлы и ожидающие загрузки данные могут занимать больше лимита; уведомить пользователя |
| Место на локальном диске | Останавливать новые офлайн-записи до падения свободного места ниже 10% |

## 2. Границы первой версии

### Входит

- Авторизация в одном аккаунте Google через системный браузер.
- Монтирование и размонтирование выбранной папки без прав администратора там, где это допускает конфигурация FUSE на системе.
- Просмотр дерева «Моего диска» в файловом менеджере и терминале.
- Чтение, создание, изменение, переименование, перемещение и удаление обычных файлов и папок.
- Дисковый кэш, очередь офлайн-операций, восстановление после перезапуска.
- Закрепление файлов и папок для офлайн-доступа.
- Отображение прогресса, ожидающих операций, ошибок и конфликтов в графическом окне.
- AppImage для x86_64, проверенный в GNOME и KDE Plasma.

### Откладывается

- Несколько аккаунтов, общие диски, раздел «Доступные мне».
- Редактирование Google Docs/Sheets/Slides как локальных Office-файлов.
- Совместный доступ, управление правами и комментариями.
- Символьные и жёсткие ссылки, блокировки файлов и специальные POSIX-файлы, если их нельзя реализовать корректно. Для неподдерживаемой операции приложение должно возвращать явную ошибку.

## 3. Архитектура

```text
Файловый менеджер / редактор / терминал
                  │
             Linux VFS / FUSE
                  │
        Go-процесс файловой системы
          ├─ таблица inode ↔ fileId
          ├─ кэш метаданных и содержимого
          ├─ локальная очередь операций
          └─ адаптер Google Drive API
                  │
              Google Drive

Qt-окно ── локальный IPC ── управление процессом, настройками и состоянием
```

Рекомендуемая структура Go-модуля:

| Каталог | Ответственность |
|---|---|
| `cmd/drivefs` | Запуск процесса файловой системы и монтирование |
| `cmd/driveapp` | Запуск Qt-приложения и управление монтированием |
| `internal/domain` | Типы объектов, версии, операции, правила конфликтов и состояний |
| `internal/driveapi` | OAuth, HTTP-запросы, пагинация, загрузка, скачивание, обработка ошибок Google |
| `internal/store` | SQLite, журнал операций и управление кэшем |
| `internal/fusefs` | FUSE-операции и отображение возможностей Drive в файловую систему |
| `internal/app` | Qt-окно, уведомления, настройки, запуск и остановка монтирования |

Файловая система и GUI работают как отдельные процессы. Связь между ними — локальный IPC с ограниченным доступом: GUI получает состояние и отправляет команды, а файловая система продолжает работу независимо от закрытия окна. Общие типы и правила остаются в Go-пакетах; сетевые запросы и работа с SQLite не выполняются в GUI-потоке.

### Кандидаты библиотек

- **FUSE:** начать с прототипа на [`go-fuse/v2`](https://github.com/hanwen/go-fuse). Проверить нужные операции, параллельные запросы, ошибки и восстановление после сбоев до закрепления выбора.
- **HTTP и фоновые задачи:** стандартный `net/http`, долгоживущий `http.Client`, `context.Context` для отмены, ограничение параллелизма и повторные попытки с задержкой.
- **База данных:** SQLite через `database/sql` и выбранный после прототипа драйвер. Очередь и смена состояний должны обновляться транзакционно; отдельно проверить долговечность записи и восстановление после аварийного завершения.
- **GUI:** Qt 6 Widgets через [`MIQT`](https://github.com/mappu/miqt). На раннем прототипе проверить нужные виджеты, `QSystemTrayIcon`, обновление состояния из фоновых задач и сборку AppImage. Привязка использует CGO и требует C++/Qt-инструменты при сборке.
- **Секреты:** системное хранилище секретов через подходящий для GNOME и KDE механизм. Токены не записывать в журналы или обычные настройки; интеграцию проверить в обеих средах.

FUSE-обработчики не должны держать общую блокировку индекса во время сетевого запроса. Сетевые задачи и GUI не должны блокировать друг друга. Отдельно определить лимиты числа запросов к Drive и число одновременных открытых файлов.

## 4. Модель данных и файловая семантика

Drive `fileId` — основной идентификатор объекта. Путь и имя могут измениться, а одинаковые имена внутри папки Drive возможны. SQLite хранит `fileId`, родительский ID, локальный inode, отображаемое имя, тип, размер, версию, время изменения, состояние кэша и признак «Доступно офлайн». Совпадающие имена получают устойчивый суффикс, который не изменяется произвольно после перезапуска.

Нужно письменно определить результат каждой существенной операции FUSE:

| Операция | Правило первой версии |
|---|---|
| `readdir`, `getattr` | Отвечать по индексу; обновлять его в фоне по журналу Drive |
| `open`, `read` | Читать выбранную версию файла; использовать кэш, при необходимости загрузить данные |
| `write` | Менять локальную рабочую копию; никогда не перезаписывать единственный экземпляр ожидающих загрузки данных |
| `flush`, `fsync` | Завершать долговременную локальную запись и фиксировать операцию в очереди; при наличии сети отдельно пытаться отправить изменение |
| `rename` | Сохранять идентичность `fileId`; перенос в другую папку отображать как изменение родителя |
| `unlink`, `rmdir` | Ставить перенос в корзину в очередь; для каталогов учитывать вложенные объекты |
| Необеспечиваемые POSIX-возможности | Возвращать соответствующую ошибку, а не сообщать об успехе без выполнения |

**Важная семантика:** успешное сохранение в офлайне гарантирует долговременную локальную копию, а не немедленную запись в Google Drive. В интерфейсе всегда показывать количество операций в ожидании. В документации это различие описать явно.

## 5. Кэш и офлайн-очередь

Разделить хранилище на три класса:

1. **Вытесняемый кэш:** недавно прочитанные файлы; суммарный лимит по умолчанию 1 ГБ.
2. **Закреплённые данные:** файлы и папки с командой «Доступно офлайн»; могут превышать обычный лимит.
3. **Неотправленные изменения:** рабочие копии и журнал операций; не вытесняются до подтверждённой отправки или явного разрешения конфликта.

Перед новой офлайн-записью оценивать доступное место. Если после неё свободного места останется менее 10%, возвращать ошибку записи и показывать уведомление. При превышении 1 ГБ закреплёнными или неотправленными данными увеличивать фактическое занятие диска с уведомлением, а не удалять эти данные.

Каждая операция очереди имеет устойчивый ID, тип, локальную версию, исходный удалённый `fileId` и версию, ожидаемый результат и состояние: `prepared → queued → uploading → committed` либо `conflict/error`. После перезапуска незавершённые операции сверяются с Drive прежде, чем повторяться, чтобы не создавать дубликаты. Большие файлы загружать через resumable upload.

## 6. Изменения на стороне Google Drive

При первой индексации получить стартовый токен изменений, обойти дерево «Моего диска» с пагинацией и затем применить изменения, накопившиеся за время обхода. Далее периодически читать `changes.list`. Новый токен сохранять только после успешного применения всей соответствующей порции данных. Когда изменился файл с локальными неотправленными правками, не перезаписывать ни одну версию: создать локальное конфликтное имя, сохранить обе версии и уведомить пользователя. [Руководство по изменениям Drive](https://developers.google.com/workspace/drive/api/guides/manage-changes).

Для временных ошибок и ограничений частоты запросов применять задержку с экспоненциальным увеличением и разбросом. Ошибку прав доступа, отзыв токена и нехватку места показывать как отдельные состояния. [Обработка ошибок Drive API](https://developers.google.com/workspace/drive/api/guides/handle-errors).

## 7. OAuth и требования Google

Создать проект Google Cloud, включить Drive API, настроить экран согласия и OAuth-клиент типа Desktop app. Авторизация — через системный браузер, loopback callback, PKCE и проверку `state`. Для полного чтения и записи в существующем «Моём диске» нужен scope `drive`; это restricted scope. Для публичного выпуска предусмотреть проверку Google и связанные требования к безопасности как отдельный календарный этап. [OAuth для desktop-приложений](https://developers.google.com/identity/protocols/oauth2/native-app), [scopes Drive](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

## 8. Графический интерфейс и AppImage

Окно должно позволять выбрать точку монтирования и лимит кэша, войти в аккаунт, видеть состояние сети и монтирования, очередь, конфликты и занятое место, закреплять файлы и папки для офлайна, размонтировать диск и выходить из аккаунта. При очередном запуске приложения диск монтируется в сохранённую папку автоматически.

Значок состояния реализовать через `QSystemTrayIcon` и проверить поддержку в выбранной Go-привязке. В KDE Plasma проверить отображение в системном трее. В GNOME значок может требовать соответствующего расширения; поэтому приложение должно оставаться доступным через обычный запуск окна и системные уведомления, даже если значок не отображается. [Документация Qt о системном трее](https://doc.qt.io/qt-6/qsystemtrayicon.html).

Упаковать в AppImage необходимые библиотеки и плагины Qt, включая платформенные плагины для X11 и Wayland; проверить условия лицензий выбранных модулей Qt при распространении. [Развёртывание Qt](https://doc.qt.io/qt-6/deployment.html), [лицензирование Qt](https://doc.qt.io/qt-6/licensing.html).

Проверить AppImage на чистых x86_64-системах GNOME и KDE: обычный запуск, режим распаковки, работу FUSE, доступ к системному хранилищу секретов, повторное открытие окна, размонтирование и обновление AppImage. Формат AppImage сам использует FUSE при обычном запуске, поэтому зависимость от него нужно явно проверить в установочных сценариях. [Архитектура AppImage](https://docs.appimage.org/reference/architecture.html).

## 9. Этапы и критерии приёмки

| Этап | Оценка для одного опытного разработчика | Результат |
|---|---:|---|
| Спецификация и прототип FUSE на Go | 2–3 недели | Монтируемый каталог; проверены чтение, запись, `fsync`, `rename` и ошибки |
| OAuth и адаптер Drive API | 2–3 недели | Вход, список файлов, скачивание и возобновляемая загрузка |
| Индекс, кэш и чтение | 3–5 недель | Просмотр дерева и устойчивое чтение файлов онлайн и из кэша |
| Запись, офлайн-очередь и конфликты | 5–8 недель | Данные переживают перезапуск и отправляются без дубликатов |
| Qt GUI, закрепление офлайн и AppImage | 3–5 недель | Пользователь управляет монтированием и видит состояние операций |
| Нагрузочные проверки и исправления | 3–5 недель | Выпускной кандидат |

**Ориентир:** около 4–7 месяцев на первый публичный выпуск. Это предварительная оценка из исходного плана; после прототипов FUSE и Qt/AppImage её следует обновить для выбранного стека. Проверка OAuth-приложения Google не включена в срок реализации.

### Обязательные сценарии проверки

- Сохранить файл без сети, закрыть приложение, запустить снова, подключиться к сети: в Drive появляется ровно одна новая версия.
- Изменить тот же файл в Drive во время офлайн-работы: обе версии сохраняются рядом, пользователь получает уведомление.
- Прервать загрузку большого файла и перезапустить приложение: передача продолжается или безопасно начинается заново без дубликата.
- Закрепить папку размером более 1 ГБ: данные остаются доступны офлайн, пользователь видит превышение обычного лимита кэша.
- Попытаться записать данные при достижении порога 10% свободного места: запись завершается явной ошибкой, ранее сохранённые изменения остаются целыми.
- Сохранить файл из редактора, который пишет временный файл и затем выполняет `rename`.
- Проверить каталог с тысячами объектов, совпадающие имена, большие файлы, одновременное чтение, удаление папки, потерю прав доступа и истечение OAuth-токена.
- Проверить запуск AppImage и работу окна в GNOME и KDE Plasma как с видимым значком в трее, так и без него.

## 10. Следующий практический шаг

Создать Go-модуль и короткий прототип файловой системы на Go. Прототип должен монтировать выбранную папку, читать тестовый файл, принимать запись в долговременную локальную очередь и корректно восстанавливаться после принудительного завершения процесса. Параллельно собрать минимальное окно Qt с управлением монтированием и значком состояния, затем проверить его упаковку в AppImage. По результатам закрепить FUSE-библиотеку, Go-привязку к Qt, схему SQLite и точную семантику сохранения.
