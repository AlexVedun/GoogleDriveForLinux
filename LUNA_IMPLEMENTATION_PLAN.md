# Пошаговый план реализации Google Drive for Linux на Go и Qt

**Дата:** 30 октября 2026 года  
**Основа:** [план проекта](plan-google-drive-linux-go-qt.md)  
**Назначение:** рабочая инструкция для Luna от пустого каталога до проверенного AppImage для Linux x86_64.

## 0. Как выполнять этот план

1. Выполнять шаги 1–21 по порядку. Каждый шаг завершать работающим, проверяемым состоянием и **отдельным коммитом**. Не объединять несколько шагов в один коммит и не оставлять завершённый шаг без коммита. Если шаг слишком велик, делить его на меньшие коммиты с тем же порядком зависимостей.
2. Перед коммитом запускать относящиеся к шагу проверки; после коммита записывать в рабочий журнал: хеш коммита, что проверено, что не проверено и почему. Проверять чистоту рабочего дерева. Не включать в коммиты токены, OAuth-секреты, SQLite с данными пользователя, содержимое кэша, журналы, AppImage и другие сборочные артефакты.
3. Если доступ к Google Cloud, тестовому аккаунту, `/dev/fuse`, GNOME или KDE отсутствует, выполнить все независимые задачи и тесты с локальным поддельным Drive API. Явно пометить недоступную живую проверку; не выдавать имитацию за подтверждение работы с настоящим аккаунтом.
4. Не менять согласованный объём первой версии без фиксации причины в отдельном решении. Важнейший контракт: успешные `flush` и `fsync` подтверждают **долговечную локальную запись**, а не отправку в Google Drive. Ни один путь ошибки, вытеснение кэша или повторный запуск не должен уничтожать неотправленные данные.
5. После каждого шага обновлять краткий `docs/progress.md`: выполненные критерии, команды проверки, известные ограничения, следующий шаг. Этот файл входит в коммит соответствующего шага. Оценку 4–7 месяцев из исходного документа пересмотреть после технических прототипов.

### Граница версии 1

Один Google-аккаунт, только «Мой диск», обычные файлы и папки, чтение и запись, офлайн-очередь, конфликты, закрепление для офлайна, Qt-окно и AppImage x86_64. Общие диски, «Доступные мне», редактирование Docs/Sheets/Slides как Office-файлов, права доступа, ссылки и специальные POSIX-объекты не реализовывать. Для неподдерживаемой файловой операции возвращать явную ошибку.

### Критерии, общие для всех шагов

- Команды `go test ./...` и `go vet ./...` проходят для затронутых пакетов; тесты, требующие FUSE или GUI, отмечены и запускаются отдельно в подходящей среде.
- Новая логика разделена по ответственностям: `cmd/drivefs`, `cmd/driveapp`, `internal/domain`, `internal/driveapi`, `internal/store`, `internal/fusefs`, `internal/app`. Добавлять небольшие пакеты по необходимости, не строить абстракции заранее.
- Сетевые запросы отменяются через `context.Context`, имеют тайм-аут и ограниченную параллельность. Ни FUSE-обработчик, ни Qt GUI-поток не ждут сеть, удерживая глобальную блокировку индекса.
- Ошибки и пользовательские состояния различают: нет сети, нужна повторная авторизация, нет прав, исчерпана квота Drive, исчерпано локальное место, конфликт, временная ошибка и необратимая ошибка.

## 12. Чтение и вытесняемый кэш

**Сделать:** читать конкретную зафиксированную версию файла; качать по частям или в локальный файл без загрузки всего содержимого в память. Проверять размер/контрольную сумму, когда Drive предоставляет их. Не подменять байты уже открытого дескриптора новой удалённой версией. Ограничить вытесняемый кэш настраиваемым значением (по умолчанию 1 ГБ) и вытеснять только незакреплённые, чистые и неиспользуемые данные. **Коммит:** `feat: read Drive files through bounded disk cache`.

## 13. Локальное создание и запись через FUSE

**Сделать:** `create`, `write`, `truncate`, `flush`, `fsync`, `release` связать с долговечным хранилищем и очередью. После успешного `flush`/`fsync` содержимое и операция доступны после перезапуска; сетевой результат от этих вызовов не зависит. Повторный `flush` того же дескриптора не создаёт дублирующую операцию. Учесть запись из нескольких дескрипторов и сериализацию конфликтующих локальных изменений. В GUI и документации явно показывать «сохранено локально, ожидает отправки».

**Проверить:** офлайн-создание и редактирование, редактор с временным файлом и `rename`, `SIGKILL` сразу после успешного `fsync`, отсутствие новых операций после повторного `flush`, возврат ошибки при невозможной локальной долговечной записи.

**Коммит:** `feat: persist local file writes before acknowledging FUSE`.

## 14. Папки, переименование и удаление

**Сделать:** `mkdir`, `rename`, `unlink`, `rmdir` выполнять сначала локально и заносить в очередь с зависимостями: ребёнок не создаётся в Drive раньше родителя; перенос не теряет `fileId`; удаление превращается в перенос в корзину Drive. Реализовать POSIX `ENOTEMPTY` и сценарий рекурсивного удаления последовательными вызовами. Сверять capabilities и возвращать предсказуемую ошибку, если операция заведомо запрещена, сохраняя уже подтверждённые локальные данные.

**Проверить:** переименование и перенос в офлайне, создание и удаление до первой отправки, удаление папки с детьми из файлового менеджера, временный файл → атомарная замена, перезапуск на каждом переходе очереди.

**Коммит:** `feat: queue folder rename move and trash operations`.

## 15. Отправка очереди и восстановление загрузки

**Сделать:** worker обрабатывает операции по зависимостям и состояниям `prepared → queued → uploading → committed` или `conflict/error`. Для новых обычных файлов заранее получать и сохранять Drive ID, где API это допускает; использовать стабильный ID операции и `appProperties` для сверки. Для больших файлов сохранять URI resumable session и после сбоя сначала запрашивать статус: завершено, `308` с диапазоном или истёкшая `404` с безопасной повторной инициацией. Не делать слепой повтор `files.create` после неизвестного результата. После ответа с неизвестным исходом сначала сверить объект в Drive; подтверждать операцию только после проверки результата.

**Проверить:** разрыв до и после успешного ответа, `SIGKILL` на каждой стадии, истёкшая сессия, повторная отправка без второго файла, зависимые операции. Если API не позволяет доказать отсутствие дубликата в отдельном случае, останавливать его как «требует сверки», не объявлять успех.

**Коммит:** `feat: sync queued operations with resumable recovery`.

## 16. Конфликты и гонки удалённых изменений

**Сделать:** перед обновлением сверять удалённую `version`/контрольную сумму с базовой версией локальной правки; изменения из `changes.list` должны переводить объект с локальной очередью в конфликт. Локальную версию сохранять как устойчивую соседнюю конфликтную копию, удалённую оставлять доступной; при синхронизации создавать отдельный файл для локальной копии, а не затирать обнаруженную удалённую версию. В GUI показать обе версии и действие пользователя. Отдельно исследовать гонку между проверкой версии и `files.update`: проверить, поддерживает ли используемый API нужное условное обновление; если атомарного условия нет, задокументировать ограничение и безопасную политику для неоднозначного исхода. Не обещать доказанную защиту от гонки без живого теста.

**Проверить:** офлайн-правка + изменение того же файла в Drive, два локальных изменения, rename при конфликте, перезапуск в состоянии `conflict`, одновременное удалённое изменение во время отправки. Обе версии доступны и ни одна не вытеснена.

**Коммит:** `feat: preserve both versions on sync conflicts`.

## 17. Закрепление офлайн и нехватка места

**Сделать:** закрепление файла и рекурсивное закрепление папки; новые дети закреплённой папки наследуют правило. Показывать ход скачивания и состояние «готово офлайн» только после полной локальной проверки. Закреплённые и неотправленные данные исключить из лимита вытесняемого кэша. Перед каждой новой офлайн-записью оценивать свободное место после операции; если осталось бы менее 10%, вернуть ошибку и уведомить пользователя. Уведомлять, когда закреплённые/неотправленные данные превышают установленный лимит.

**Проверить:** папка более 1 ГБ, появление нового ребёнка, отмена закрепления, низкое место, одновременные записи при пороге, сохранность ранее подтверждённых данных.

**Коммит:** `feat: add offline pins and disk space guard`.

## 18. Локальный IPC и жизненный цикл процессов

Повторный запуск GUI подключается к работающему `drivefs`; закрытие окна не останавливает монтирование. Отдельное действие «Выход» корректно размонтирует и завершает процессы, не удаляя неотправленные данные. Повторный запуск не создаёт второй процесс или второе монтирование.

**Проверить:** отключение GUI при активной загрузке, перезапуск GUI, сбой `drivefs`, занятый socket, неверные права, повторное нажатие mount/unmount, выход при ожидающих операциях.

## Матрица приёмки перед выпуском

| Сценарий | Наблюдаемый результат |
|---|---|
| Офлайн-запись → успешный `fsync` → `SIGKILL` → запуск → сеть | Локальные байты сохранились, в Drive создана ровно одна подтверждённая версия |
| Офлайн-правка и параллельное изменение в Drive | Обе версии доступны рядом, есть уведомление, удалённая версия не перезаписана при обнаруженном конфликте |
| Большой файл и разрыв загрузки | Загрузка продолжается с подтверждённого диапазона либо безопасно начинается заново; нет второго объекта |
| Редактор пишет временный файл и делает `rename` | Окончательное имя и содержимое совпадают локально и после синхронизации |
| Папка более 1 ГБ закреплена офлайн | Содержимое остаётся доступным; UI показывает превышение обычного лимита |
| Свободное место пересекло бы порог 10% | Новая запись отклонена явно; старые подтверждённые данные целы |
| Тысячи объектов, совпадающие имена | Полный список, стабильные суффиксы и inode после перезапуска |
| Ошибки 401, 403, 404, 429, 5xx | Разные состояния и допустимые повторы; нет бесконечного быстрого цикла |
| GNOME и KDE Plasma, X11/Wayland где доступны | Окно, монтирование, уведомления, повторное открытие; отсутствие трея не блокирует управление |
| AppImage обычный и извлечённый | Запуск, OAuth, FUSE, хранилище секретов, размонтирование и выход работают по заявленному сценарию |
